# 04. 技術選定（筋トレ管理アプリ）

このドキュメントは、[03_データ設計.md](03_%E3%83%87%E3%83%BC%E3%82%BF%E8%A8%AD%E8%A8%88.md) までで整理した内容を、実際にどの技術で実装するか決めるための資料です。

ブログ向けに工程が分かるよう、これまでの設計資料は残したまま、このファイルを独立した成果物として作成します。

## 0. このフェーズの目的
- どの技術でアプリを作るか決める
- 学習しやすさと実装しやすさのバランスを取る
- 次の「実装開始」で迷わない状態にする

## 1. 技術選定で考えること
技術選定では、次の観点で判断します。

1. 学習コストは高すぎないか
2. 今回の要件を無理なく満たせるか
3. 後から拡張しやすいか
4. Windows 環境で進めやすいか
5. ブログで学習過程を説明しやすいか

学習ポイント:
- 技術選定は「流行っているものを選ぶ作業」ではありません
- 今回の目的に対して、過不足の少ない構成を選ぶ作業です

## 2. 今回のアプリに必要なもの
今回のアプリで最低限必要なのは次の機能です。

- スマホ優先のWeb画面
- 入力とグラフ表示が同じ画面にあるUI
- ユーザーごとのメニューグループ管理
- 複数テーブルの保存
- 記録一覧やグラフ表示用のデータ取得

つまり、大きく分けると次の3層が必要です。

- フロントエンド: 画面を作る
- バックエンド: データの保存・取得を行う
- データベース: データを保持する

## 3. 候補構成

### 候補A: Next.js + SQLite + Prisma

#### 構成
- フロントエンド: Next.js
- バックエンド: Next.js Route Handler / Server Actions
- DB: SQLite
- ORM: Prisma

#### メリット
- 1つのプロジェクトで画面とAPIをまとめやすい
- React ベースで画面設計とつながりやすい
- SQLite はローカル開発が簡単
- Prisma はデータ設計をコードにしやすい
- 学習記事にしやすい構成

#### 注意点
- Next.js は最初は少し用語が多い
- App Router の概念に慣れる必要がある

#### 向いている理由
- 今回はスマホ向けWebアプリを作りたい
- 実装量を増やしすぎず、将来の拡張にも対応しやすい

### 候補B: React + Express + SQLite

#### 構成
- フロントエンド: React + Vite
- バックエンド: Express
- DB: SQLite

#### メリット
- フロントとバックの役割が分かりやすい
- 学習として「フロント」と「API」を分けて理解しやすい

#### 注意点
- プロジェクトが分かれるぶん管理対象が増える
- 初心者には設定作業がやや多い
- 今回の規模では少し構成が重い

#### 向いている場面
- API とフロントを明確に分けて学びたい場合

### 候補C: Firebase / Supabase 中心構成

#### 構成
- フロントエンド: Next.js または React
- バックエンド: BaaS の機能を利用
- DB: Supabase Postgres など

#### メリット
- 認証やクラウド保存に進みやすい
- 将来の複数ユーザー対応に強い

#### 注意点
- 最初の学習ではサービス固有の概念が増える
- オフラインではないが、クラウド前提の理解が必要
- 今回の MVP では少しオーバー気味

#### 向いている場面
- 早めにログインや共有機能も扱いたい場合

## 4. 今回の推奨構成
今回の学習と要件を考えると、最もバランスがよいのは次です。

### 推奨
- フロントエンド: Next.js
- スタイリング: Tailwind CSS
- バックエンド: Next.js の Route Handler または Server Actions
- DB: SQLite
- ORM: Prisma
- グラフ描画: Recharts
- フォーム管理: まずは React の基本状態管理で開始

## 5. なぜこの構成を推すのか

### 5-1. Next.js
理由:
- 画面とデータ取得の距離が近い
- 後から API を足しやすい
- PC / スマホ両対応の Web アプリを作りやすい
- React の学習にもつながる

### 5-2. SQLite
理由:
- 今回はローカル中心で進められる
- セットアップが軽い
- MVP を早く動かしやすい

### 5-3. Prisma
理由:
- [03_データ設計.md](03_%E3%83%87%E3%83%BC%E3%82%BF%E8%A8%AD%E8%A8%88.md) の内容を、そのままスキーマ定義に落とし込みやすい
- テーブル関係がコードで見やすい
- マイグレーション管理を学びやすい

### 5-4. Tailwind CSS
理由:
- スマホ優先のレイアウトを作りやすい
- 細かい CSS 設計に時間を取られにくい
- 学習初期で UI 作りの速度を上げやすい

### 5-5. Recharts
理由:
- React と相性がよい
- 重量推移や回数推移のグラフが比較的簡単に描ける
- ホーム画面の簡易グラフと詳細グラフ画面の両方に使いやすい

学習ポイント:
- 最初から完璧な構成を目指す必要はありません
- ただし、機能ごとに分ける意識を持つと後から見返しやすいです

## 7. 今回はまだ採用しないもの
MVP では次のものは後回しでよいです。

- Redux などの大きな状態管理ライブラリ
- 複雑な認証基盤
- クラウドDB
- リアルタイム同期
- 高度なキャッシュ戦略

理由:
- まずは「記録できる」「保存できる」「見返せる」を完成させる方が重要だから
- 複雑な道具を早く入れすぎると、学習負荷が上がるから

## 8. この構成で実装するときの流れ
次の順番で進めると学習しやすいです。

1. Next.js プロジェクトを作る
2. Tailwind CSS を使える状態にする
3. Prisma と SQLite を設定する
4. [03_データ設計.md](03_%E3%83%87%E3%83%BC%E3%82%BF%E8%A8%AD%E8%A8%88.md) を schema.prisma に落とす
5. ホーム画面の入力フローを仮実装する
6. 記録保存と一覧取得を作る
7. グラフ表示を追加する

- 後から複数ユーザー対応へ伸ばしやすい
