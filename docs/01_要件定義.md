# 01. 要件定義（筋トレ管理アプリ）

このドキュメントは、実際の開発現場で行う順番に近い形で、要件定義を進めるためのワークシートです。

## 0. このフェーズの目的
- 何を作るかを明確にする（機能の境界を決める）
- 誰のどんな課題を解決するかを明確にする
- 後の設計・実装で迷わないための判断基準を作る

## 1. 背景と目的
まず「なぜこのアプリを作るのか」を言語化します。

### 1-1. 背景
- 記録は残しているが数値の羅列になりやすく、成長実感を得にくい
- 過去比較や仲間比較がしづらく、モチベーション維持につながりにくい
- 毎回メニュー名と回数を手入力しており、入力の手間が継続の小さな障害になっている

### 1-2. 解決したい課題
- 課題1: 直感的に記録できず、入力行為にストレスがある
- 課題2: メニュー名だけでは運動内容を思い出しにくい
- 課題3: 成長度が見えにくく、継続の実感が得にくい

### 1-3. プロジェクト目的
- トレーニング記録を素早く残せる体験を作り、継続しやすくする
- 過去比較と進捗可視化で、成長を実感できる状態を作る
- 将来的に社内の仲間とも比較できる拡張を見据えた土台を作る

## 2. 対象ユーザー定義
誰のためのアプリかを具体化します。

### 2-1. メインユーザー
- 年齢層: 社会人（まずは本人利用を想定）
- トレーニング経験: 初級〜中級
- 使う場面: ジム直後や帰宅後にスマホで短時間入力、PCで振り返り

### 2-2. ユーザーの行動
- 記録するタイミング: トレーニング直後
- 何を見返したいか: 種目ごとの重量・回数の推移、前回記録との差分
- 何が面倒か: 毎回のメニュー名手入力、同じ構成の反復入力

## 3. スコープ定義（MVP）
最初に作る最小機能（MVP）を決めます。MVPは「学習のために小さく作って完成させる」ために重要です。

### 3-1. 今回やること（In Scope）
- [x] 種目の登録
- [x] トレーニング記録（重量・回数・セット）
- [x] 日付ごとの記録一覧
- [x] 過去記録の確認
- [x] 検索・フィルタ（日付、種目）
- [x] 進捗グラフ（最低限: 種目ごとの重量推移）
- [x] 入力補助（登録済み種目の候補表示）

### 3-2. 今回やらないこと（Out of Scope）
- [ ] SNS共有
- [ ] AIフォーム解析
- [ ] ウェアラブル連携
- [ ] 会社内ランキングや本格的な対人比較機能（将来対応）
- [ ] 通知やリマインダー

## 4. 機能要件
「アプリが何をできるべきか」を定義します。

### 4-1. ユーザーストーリー
形式: 「<ユーザー>として、<目的>のために、<機能>したい」

- US-01: 利用者として、あとで振り返るために、トレーニング内容を記録したい
- US-02: 利用者として、入力時間を短くするために、登録済み種目を候補から選んで記録したい
- US-03: 利用者として、成長を実感するために、種目ごとの重量や回数の推移を見たい
- US-04: 利用者として、前回との差を確認するために、日付や種目で絞り込んで過去記録を探したい

### 4-2. 機能一覧
- F-01: 種目マスタを作成・編集・削除できる
- F-02: 1回のトレーニングセッションを作成できる
- F-03: セッションに複数セットを登録できる
- F-04: 日付・種目で記録を検索できる
- F-05: 記録入力時に種目名の候補を表示し、選択入力できる
- F-06: 種目ごとの進捗グラフ（重量推移）を表示できる

### 4-3. 受け入れ条件（Acceptance Criteria）
例（F-02）
- Given: 利用者が記録画面を開いている
- When: 日付と種目を選んで保存する
- Then: 記録一覧に新しいセッションが表示される

追加例（F-05）
- Given: 利用者が種目入力欄を選択している
- When: 1文字以上入力する
- Then: 登録済み種目の候補が表示され、候補選択で入力を確定できる

追加例（F-06）
- Given: 利用者が特定種目の詳細画面を開いている
- When: 期間を指定して表示する
- Then: 時系列で重量推移がグラフ表示される

## 5. 非機能要件
品質の要件（速さ、使いやすさ、保守性など）を定義します。

- N-01: 主要画面の表示は3秒以内
- N-02: スマホ幅（375px程度）で操作できる
- N-02-補足: PC表示でも同じデータを閲覧できるレスポンシブ対応
- N-03: 入力エラー時に具体的なメッセージを表示する
- N-04: コードは機能ごとにフォルダ分割する

## 6. データ要件（最小）
最初に必要なデータだけ定義します。

- Exercise（種目）
  - id
  - name
  - bodyPart（胸、背中、脚 など）
- WorkoutSession（1日の記録）
  - id
  - date
  - note
- WorkoutSet（セット）
  - id
  - sessionId
  - exerciseId
  - weight
  - reps
  - setOrder

## 7. 制約と前提
- 開発期間: 学習を主目的として段階開発（まずMVP完成を最優先）
- 学習優先事項: 要件定義 -> 画面設計 -> データ設計 -> 実装の順で理解する
- 利用技術の候補: Webアプリ（スマホ優先、PC対応）

## 8. 成功指標（KPI）
- 1週間で最低3回の記録を継続できる
- 1回の記録入力を1分以内で完了できる
- 前回比が確認できる画面操作を30秒以内で完了できる

## 9. 未決事項（次回決める）
- 認証は必要か
- オフライン対応は必要か
- 社内比較機能をMVPに含めるか（初版は除外予定）

## 10. 決定理由メモ
- 入力補助をMVPに含めた理由: 継続阻害要因が「入力の面倒さ」だから
- グラフをMVPに含めた理由: 課題が「成長実感の不足」だから
- 比較機能を将来対応にした理由: 実装難易度が高く、まずは単独利用で価値検証するため

## 進め方（学習向け）
1. まず空欄を埋める
2. 迷ったら「MVPを小さくする」方向で判断
3. 決めた理由を1行で残す（将来の自分のため）
